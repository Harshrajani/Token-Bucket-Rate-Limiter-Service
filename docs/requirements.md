# Requirements.md

# Token Bucket Rate Limiter Service

## 1. Overview

The Token Bucket Rate Limiter Service is a standalone backend service responsible for determining whether an incoming request from a client should be **ALLOWED** or **DENIED** based on a configurable rate-limiting policy.

Version 1 focuses on the Token Bucket algorithm with PostgreSQL persistence and REST APIs.

---

# 2. Functional Requirements

## FR-01 — Rate Limit Decision

The system shall provide an API that accepts a client identifier and determines whether the request should be allowed.

Possible decisions:

- `ALLOWED`
- `DENIED`

The decision shall be based on the client's configured rate-limiting policy and current bucket state.

---

## FR-02 — Client Identification

Each rate-limited client shall be identified using a unique `clientId`.

Examples:

- User
- API key
- Microservice
- Application
- External client

Each client shall have at most one active rate-limiting policy.

---

## FR-03 — Policy Configuration

The system shall support configurable rate-limiting policies per client.

Each policy shall contain:

- `clientId`
- `algorithm`
- `capacity`
- `refillRate`

Where:

- `capacity` represents the maximum number of tokens the bucket can hold.
- `refillRate` represents the number of tokens added per second.
- `algorithm` identifies the rate-limiting algorithm used by the client.

Example:

    clientId   = payment-service
    algorithm  = TOKEN_BUCKET
    capacity   = 20
    refillRate = 5

---

## FR-04 — Policy Management

The system shall provide administrative APIs to manage rate-limiting policies.

### Create Policy

    POST /api/v1/admin/policies

The request shall contain:

- `clientId`
- `algorithm`
- `capacity`
- `refillRate`

The server shall generate the database identifier and manage audit timestamps.

### Get Policy

    GET /api/v1/admin/policies/{clientId}

The system shall return the policy associated with the specified client.

If the policy does not exist, the system shall return an appropriate error response.

### Update Policy

    PUT /api/v1/admin/policies/{clientId}

The system shall allow modification of the client's rate-limiting configuration.

The following fields may be updated:

- `algorithm`
- `capacity`
- `refillRate`

The following fields shall not be controlled by the client:

- `id`
- `createdAt`
- `updatedAt`

---

## FR-05 — Bucket State

Each rate-limiting policy shall have an associated bucket.

The bucket shall maintain:

- `policyId`
- `availableTokens`
- `lastRefillTime`

The bucket represents runtime state rather than configuration.

---

## FR-06 — Persistent State

Rate-limiting state shall persist across application restarts.

The system shall use PostgreSQL for persistent storage.

The following information shall be persisted:

- Rate-limit policies
- Bucket state

After a service restart, the system shall be able to continue rate limiting using the previously persisted state.

---

## FR-07 — Token Bucket Algorithm

Version 1 shall implement the Token Bucket algorithm.

For each incoming request:

    Load Policy
        ↓
    Load Bucket
        ↓
    Calculate elapsed time
        ↓
    Calculate tokens to refill
        ↓
    Refill bucket
        ↓
    Check available tokens
        ↓
    Consume token if available
        ↓
    Persist bucket
        ↓
    Return decision

---

## FR-08 — Lazy Refill

The Token Bucket shall use lazy refill.

Tokens shall not be generated by a background scheduler.

Instead, the number of tokens to add shall be calculated when a request arrives.

Conceptually:

    elapsed time
          ↓
    tokens generated
          ↓
    current tokens + generated tokens
          ↓
    minimum(capacity)

The bucket shall never contain more tokens than its configured capacity.

---

## FR-09 — Token Consumption

A successful request shall consume exactly one token.

If:

    availableTokens > 0

the request shall be:

    ALLOWED

and one token shall be consumed.

If:

    availableTokens == 0

the request shall be:

    DENIED

and no token shall be consumed.

---

## FR-10 — Rate Limit Check API

The system shall expose:

    POST /api/v1/rate-limit/check

Request:

    {
      "clientId": "user-123"
    }

The system shall use the `clientId` to locate the corresponding policy and bucket.

---

## FR-11 — Allowed Response

When a request is allowed, the system shall return rate-limit metadata.

Example:

    {
      "status": "ALLOWED",
      "limit": 20,
      "remaining": 14
    }

Where:

- `status` represents the decision.
- `limit` represents the configured bucket capacity.
- `remaining` represents the number of tokens remaining after the request.

---

## FR-12 — Denied Response

When a request is denied, the system shall return rate-limit metadata.

Example:

    {
      "status": "DENIED",
      "limit": 20,
      "remaining": 0,
      "retryAfter": 2
    }

Where:

- `retryAfter` represents the estimated number of seconds before a request may become available.

---

## FR-13 — Rate Limit Status

Rate-limit decisions shall be represented using a strongly typed enum rather than arbitrary strings.

Supported statuses:

    ALLOWED
    DENIED

---

## FR-14 — Validation

Incoming API requests shall be validated before business logic is executed.

### Client ID

- Must not be null.
- Must not be blank.

### Algorithm

- Must not be null.
- Must represent a supported rate-limiting algorithm.

### Capacity

- Must not be null.
- Must be greater than zero.

### Refill Rate

- Must not be null.
- Must be greater than zero.

Invalid requests shall result in an appropriate client error response.

---

## FR-15 — Duplicate Policy Prevention

A client shall not have multiple rate-limiting policies.

The application shall reject attempts to create a policy for a client that already has one.

The database shall also enforce uniqueness of `clientId`.

---

## FR-16 — Policy and Bucket Lifecycle

A bucket shall exist for every active rate-limiting policy.

The bucket shall not exist independently of its policy.

When a policy is deleted, its associated bucket shall also be removed.

---

## FR-17 — Exception Handling

The application shall use centralized exception handling.

A global exception handler shall convert application exceptions into consistent HTTP responses.

Expected domain exceptions include:

- `PolicyNotFoundException`
- `BucketNotFoundException`
- `DuplicatePolicyException`
- `InvalidPolicyException`

Validation failures shall also be handled consistently.

---

## FR-18 — Concurrency Safety

The system shall prevent concurrent requests for the same client from consuming the same token.

For example, if only one token is available:

    Request A ──┐
                ├──> Bucket
    Request B ──┘

Only one request shall be allowed to consume that token.

The implementation shall ensure that concurrent requests cannot cause:

- Double token consumption
- Lost updates
- Incorrect remaining-token counts
- Invalid bucket state

The exact concurrency mechanism shall be finalized during implementation.

---

## FR-19 — Multiple Rate-Limiting Algorithms

The architecture shall support multiple rate-limiting algorithms.

### Version 1

- Token Bucket

### Future Versions

- Sliding Window
- Leaky Bucket
- Fixed Window

Algorithm selection shall be based on the policy associated with the client.

The Strategy Pattern shall be used when multiple algorithms are implemented.

---

## FR-20 — Repository Abstraction

Persistence access shall be separated from business logic using repository interfaces.

Required repositories:

    RateLimitPolicyRepository
    BucketRepository

Repositories shall be responsible for persistence operations and shall not contain rate-limiting business logic.

---

# 3. Non-Functional Requirements

## NFR-01 — Performance

The service should provide low-latency rate-limit decisions.

The core Token Bucket calculation should operate in constant time:

    O(1)

excluding database and network latency.

---

## NFR-02 — Reliability

The service shall provide consistent rate-limit decisions under normal operating conditions.

Persisted bucket state shall survive application restarts.

---

## NFR-03 — Consistency

The system shall maintain consistency between:

    RateLimitPolicy
           ↓
         Bucket

A bucket must correspond to a valid policy.

---

## NFR-04 — Concurrency

The system shall remain correct when multiple requests for the same client arrive concurrently.

The implementation must prevent:

- Double token consumption
- Lost updates
- Incorrect remaining-token counts
- Invalid bucket state

---

## NFR-05 — Scalability

The architecture should allow future migration from a single-instance deployment to a distributed deployment.

Future scaling options may include:

- Redis
- Distributed locking
- Multiple service instances
- Kubernetes
- Horizontal scaling

---

## NFR-06 — Maintainability

The codebase shall follow clear separation of responsibilities.

The primary layers shall be:

    Controller
        ↓
    Service
        ↓
    Strategy
        ↓
    Repository
        ↓
    Database

Each layer should have a clearly defined responsibility.

---

## NFR-07 — Extensibility

The system shall allow additional rate-limiting algorithms to be added without significantly modifying the existing orchestration logic.

The intended architecture is:

    RateLimitingStrategy
            ▲
            │
       ┌────┴────────────┐
       │                 │
    TokenBucket      SlidingWindow
     Strategy          Strategy

---

## NFR-08 — Observability

The architecture should support future integration with monitoring and observability tools.

Future capabilities may include:

- Request metrics
- Allowed request count
- Denied request count
- Latency metrics
- Error rates
- Per-client usage
- Prometheus
- Grafana

Observability is not required for the initial V1 implementation.

# 6. Error Handling Requirements

The API shall return meaningful HTTP status codes.

Expected mappings include:

| Situation | HTTP Status |
|---|---:|
| Successful creation | 201 Created |
| Successful retrieval | 200 OK |
| Successful update | 200 OK |
| Invalid request | 400 Bad Request |
| Policy not found | 404 Not Found |
| Bucket not found | 404 Not Found |
| Duplicate policy | 409 Conflict |
| Unexpected server error | 500 Internal Server Error |

The exact error response structure shall be standardized through the global exception handler.

# 8. Transaction Requirements

Operations that modify multiple pieces of related state shall be executed transactionally.

For example, creating a policy and its initial bucket should be treated as one logical operation:

    Create Policy
        ↓
    Create Bucket
        ↓
    Commit Transaction

If bucket creation fails, the policy creation should also be rolled back.

# 17. Acceptance Criteria

The V1 implementation will be considered complete when:

- A policy can be created successfully.
- Duplicate policies are rejected.
- A policy can be retrieved using `clientId`.
- A policy can be updated.
- A bucket is automatically created for a new policy.
- Bucket state persists in PostgreSQL.
- A rate-limit check can be performed for a client.
- Tokens are refilled correctly based on elapsed time.
- Requests consume exactly one token when allowed.
- Requests are denied when no token is available.
- A bucket never exceeds its configured capacity.
- Retry information is returned for denied requests.
- Invalid requests are rejected.
- Missing policies produce a 404 response.
- Duplicate policies produce a 409 response.
- Concurrent requests cannot double-spend the same token.
- Automated tests cover the core rate-limiting behavior.
- Load testing validates behavior at the initial 500+ requests-per-second target.
